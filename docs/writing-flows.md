# 플로우 작성 규칙과 자주 쓰는 명령

## 파일 구조

플로우 파일은 설정 블록과 명령 블록을 `---` 로 구분합니다.

```yaml
appId: ${APP_ID}          # 필수. 대상 앱의 패키지 이름 또는 번들 식별자
name: 게스트 로그인 검증   # 선택. 실행 결과에 표시되는 이름
tags:                     # 선택. 실행 대상을 필터링하는 태그
  - sdk
env:                      # 선택. 이 플로우에서만 사용하는 환경 변수
  RETRY_COUNT: 3
---
- launchApp
- tapOn: "로그인"
- assertVisible: "환영합니다"
```

## 자주 쓰는 명령

| 명령 | 용도 |
| --- | --- |
| `launchApp` | 앱을 실행합니다. `clearState: true` 옵션으로 상태를 초기화할 수 있습니다 |
| `clearState` | 앱의 저장 데이터를 삭제합니다 |
| `tapOn` | 텍스트, `id`, `point` 등으로 지정한 요소를 탭합니다 |
| `inputText` | 현재 포커스된 입력란에 문자열을 입력합니다 |
| `assertVisible` / `assertNotVisible` | 요소의 표시 여부를 검증합니다 |
| `extendedWaitUntil` | 조건이 충족될 때까지 최대 `timeout` 밀리초 동안 기다립니다 |
| `runFlow` | 서브플로우를 호출합니다. `when` 으로 조건 분기, `env` 로 인자 전달이 가능합니다 |
| `evalScript` | 자바스크립트 표현식을 실행합니다 |
| `takeScreenshot` | 스크린샷을 남깁니다. 실패 원인 추적에 유용합니다 |

전체 명령 목록은 Maestro MCP 의 `cheat_sheet` 도구나 [공식 레퍼런스](https://docs.maestro.dev/reference/commands)에서 확인할 수 있습니다.

## 환경 변수

`.env` 의 값은 `scripts/run.sh` 가 `-e KEY=VALUE` 형태로 전달합니다. 플로우에서는 `${KEY}` 로 참조하고, 기본값이 필요하면 `${KEY || "기본값"}` 처럼 자바스크립트 표현식을 사용합니다.

`appId` 에도 환경 변수 치환이 적용됩니다. 다만 콘솔 출력의 라벨에는 치환되기 전의 문자열이 그대로 표시되므로, 로그에 `${APP_ID}` 가 보이더라도 실제로는 값이 적용된 상태입니다.

## 태그로 실행 범위를 조절하기

같은 플래그 안에 여러 태그를 나열하면 OR 조건으로 동작하고, `--include-tags` 와 `--exclude-tags` 를 함께 쓰면 두 그룹 사이에는 AND 조건이 적용됩니다.

```bash
./scripts/run.sh .maestro --include-tags=sdk,login
./scripts/run.sh .maestro --include-tags=sdk --exclude-tags=login
```

`config.yaml` 의 `excludeTags` 에 정의한 태그는 명령행 플래그와 무관하게 항상 제외됩니다. 이 저장소에서는 `wip` 가 여기에 해당합니다.

## Unity 화면을 좌표로 조작하기

좌표를 쓰기 전에 그 화면이 정말 Unity 인지 `inspect_screen` 으로 확인하세요. DevPlay SDK 테스트 앱은 게임 본체가 그리는 화면만 Unity 이고, SDK 가 그리는 나이 입력과 약관 동의, IDP 로그인, 게스트 로그인 주의사항 화면은 네이티브라서 선택자로 다룰 수 있습니다. 좌표는 마지막 수단입니다.

Unity 로 렌더링되는 화면은 뷰 계층에 `unitySurfaceView` 하나만 노출되므로, 문구나 식별자로 요소를 지정할 수 없고 `tapOn` 의 `point` 인자에 백분율 좌표를 넘겨야 합니다. 화면 내용의 검증은 `assertWithAI` 로만 가능합니다. DevPlay SDK 테스트 앱에서 확인한 제약들은 다음과 같습니다.

**탭 재시도를 반드시 끕니다.** Maestro 는 탭 이후 뷰 계층이 바뀌지 않으면 탭이 전달되지 않은 것으로 보고 한 번 더 누릅니다. 이 앱은 화면이 어떻게 바뀌어도 뷰 계층이 항상 동일하기 때문에 재시도가 무조건 발생하고, 그러면 체크박스가 두 번 토글되어 원래 값으로 돌아가거나 드롭다운이 열렸다가 바로 닫힙니다. 모든 `tapOn` 에 `retryTapIfNoChange: false` 를 지정하고, 몇 번 누를지를 직접 정해야 합니다.

**액티비티가 다시 만들어진 직후의 첫 탭은 사라집니다.** 앱을 실행한 직후, 그리고 화면 방향이 바뀐 직후에 보내는 첫 탭은 앱에 전달되지 않습니다. 그래서 눌러도 아무 동작이 없는 위치를 먼저 한 번 눌러 이 손실을 흡수시킵니다. 이미 선택되어 있는 탭 버튼이나 대화상자의 제목 영역이 적합합니다.

**버튼은 두 번, 토글은 한 번 누릅니다.** 버튼은 두 번 눌려도 결과가 같으므로 `repeat: 2` 와 `delay` 를 지정해 탭 손실에 대비합니다. 반면 체크박스처럼 누를 때마다 값이 뒤집히는 요소는 반드시 한 번만 눌러야 하므로, 앞의 흡수용 탭으로 손실을 막아 두어야 합니다.

**가로 방향에 따라 화면이 약 5% 이동합니다.** 가로 방향이 왼쪽인지 오른쪽인지에 따라 디스플레이 컷아웃의 안전 영역이 달라지고, 화면 전체가 가로로 밀립니다. 기기를 어떻게 두었는지에 따라 방향이 결정되므로, 좌표는 두 방향에서 모두 대상 안에 들어오는 값으로 잡습니다. 폭이 좁은 체크박스는 두 방향에서 겹치는 좌표가 없을 수 있으므로, 함께 반응하는 라벨을 누르는 편이 안전합니다.

**가로 방향이 뒤집혀도 테스트는 감지하지 못합니다.** 스크린샷은 앱 자신의 좌표계로 캡처되어 기기가 물리적으로 어떤 방향이든 언제나 똑바로 찍히고, 좌표 탭도 같은 좌표계를 씁니다. 그래서 화면이 위아래가 뒤집혀 표시되어도 플로우 안에서는 판별할 방법이 없습니다. 실제 방향을 확인해야 한다면 아래 명령으로 따로 봐야 합니다.

```bash
adb shell dumpsys window | grep -m1 mRotation                                  # 디스플레이가 확정한 회전
adb shell dumpsys activity activities | grep -oE "SCREEN_ORIENTATION_[A-Z_]+"  # 앱이 요청한 방향
```

방향은 앱이 결정하므로 테스트 쪽에서 바로잡을 수 없습니다. 이 앱의 경우 매니페스트에서 `OvenUnityPlayerActivity` 가 `sensorLandscape` 로 선언되어 있고, 실행 중에는 `SCREEN_ORIENTATION_LANDSCAPE` 와 `SCREEN_ORIENTATION_REVERSE_LANDSCAPE` 를 번갈아 요청합니다. Unity 의 자동 회전이 양쪽 가로 방향을 모두 허용한 상태라서 Unity 가 기기 자세를 읽어 방향을 정하는 구조입니다. 기기를 평평하게 두면 이 판단이 역방향으로 기울어 화면이 뒤집힙니다. 기기의 자동 회전 설정 변경, `setOrientation`, `dumpsys sensorservice restrict` 로 센서 차단까지 시도해 봤지만 어느 것도 앱의 요청을 덮지 못했습니다. 방향을 하나로 고정하려면 앱의 Unity 설정에서 허용 방향을 하나만 남겨야 합니다.

**`setOrientation` 으로 방향을 고정하지 않습니다.** 이 명령은 기기의 자동 회전 설정을 끄고 회전 각도를 고정하는데, 그러면 앱의 방향 처리와 충돌해서 화면 전환이 실패합니다. 게다가 플로우가 끝난 뒤에도 그 설정이 기기에 남습니다. 시스템 설정으로는 앱의 명시적인 방향 요청을 덮을 수 없으므로 효과도 없습니다.

**`point` 의 백분율은 정수만 받습니다.** 소수를 넘기면 `NumberFormatException` 이 발생합니다. 슬라이더처럼 위치와 값이 대응하는 요소는 1% 단위의 해상도만 확보되므로, 특정 값을 정확히 지정하는 것은 어렵습니다.

**대기는 화면이 멈추는지로 판단합니다.** `waitForAnimationToEnd` 는 연속한 스크린샷이 같아질 때까지 기다립니다. 배경 연출이 없는 화면에서는 실제 조건 대기로 동작해서 대개 몇 초 안에 끝나지만, 불꽃 연출처럼 계속 재생되는 배경이 있는 화면에서는 지정한 시간을 모두 소모합니다. 후자의 경우에는 짧은 대기와 `assertWithAI` 를 `retry` 로 묶어, 화면이 확인되는 즉시 다음 단계로 넘어가게 하는 편이 낫습니다.

## 안정적인 플로우를 위한 권장 사항

- 화면 문구는 변경되기 쉬우므로, 가능하면 `id` 로 요소를 지정합니다.
- 네트워크 응답을 기다려야 하는 지점에는 `extendedWaitUntil` 을 사용하고 `timeout` 을 충분히 잡습니다.
- 로그인처럼 여러 테스트에서 반복되는 절차는 서브플로우로 분리합니다.
- 검증 실패 지점 직전에 `takeScreenshot` 을 넣어 두면 원인을 파악하기 쉬워집니다.
- 같은 요소를 여러 번 눌러야 한다면 `repeat` 명령으로 `tapOn` 을 반복하지 말고, `tapOn` 한 번에 `repeat` 과 `delay` 를 지정하세요. 전자는 반복마다 요소를 다시 찾느라 뷰 계층을 매번 조회하므로 탭 한 번에 약 1,140 ms 가 걸리고, 후자는 조회를 한 번만 합니다. 나이 입력 화면에서 19회를 누르는 경우 21,743 ms 에서 14,761 ms 로 줄었습니다. 다만 `repeat` 과 `delay` 는 환경 변수를 받지 못하고 숫자 값만 허용합니다. 참고로 식별자로 요소를 찾는 탭은 약 1,140 ms, 좌표로 누르는 탭은 약 300 ms 가 걸립니다.
- 단계별 소요 시간은 실행 결과 폴더의 `commands.json` 에서 각 명령의 `metadata.duration` 으로 확인할 수 있습니다.
